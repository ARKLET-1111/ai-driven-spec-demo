## 1. 背景とご依頼

前回の打ち合わせで、「仕様書は現在すべて人手で PowerPoint に書いている。Nemotron を使って仕様書を上手に作る方法を知りたい」とのご要望をいただきました。
本資料は、貴社の環境と同じモデル（Nemotron-3-Super 120B）と同じツール（OpenCode）を用いて、**実際に動かした結果**に基づいてお答えするものです。

## 2. 結論（3点）

1. **お手元の PowerPoint / Excel は、文字と表であれば、そのまま AI が読める形式（Markdown）に一瞬で変換できます。** 手直しはほぼ不要です。図（画像）の部分だけは、文字の読み取り（OCR）と人の確認が必要です。
2. **「見本を1本添える」「章立てを指定する」「決めていないことは【要確認】と書かせる」の3点を守れば、Nemotron でも実装に使える仕様書が書けます。** 1本あたり 2〜5分でした。
3. **その仕様書を一字も直さずに渡したところ、実装 → 単体試験 24 件全件合格 → 行カバレッジ 97.1% まで、人手ゼロで到達しました**（27分）。仕様書の形さえ整っていれば、実装工程はローカルLLMに任せられます。

## 3. 進め方（3ステップ）

```
PowerPoint / Excel ──(変換ツール)──▶ Markdown ──(Nemotron)──▶ 仕様書 ──(Nemotron ＋ 固定の手順)──▶ 実装・単体試験
```

| ステップ | 内容 | 使うもの |
|---|---|---|
| ① 変換 | `docling 仕様書.pptx --to md` の1行で Markdown に変換します | Docling（IBM が公開する無償の変換ツール。**貴社のPC内だけで動作し、資料は外部に出ません**） |
| ② 仕様書作成 | 見本の仕様書と章立てを添えて、Nemotron に仕様書を書かせます | プロンプト（リポジトリ `docs/03` に全文） |
| ③ 実装 | 仕様書・守るべきルール・固定したビルド手順を渡して Nemotron に実装させ、単体試験とカバレッジまで自動で回します。**結果は同じコマンドで人が再確認できます** | リポジトリ `pattern3_impl/` |

要件定義の段階からであれば、②の入力を「要件定義書（PowerPoint から変換）」に替えるだけで同じ流れになります。今回はこの形でも検証し、要件と実装の対応表（要件トレース表）まで自動生成できることを確認しました。

## 4. 仕様書に含めていただきたい項目（AI が読みやすい形）

AI にとって仕様書は**唯一の入力**です。人どうしなら通じる「いつものやり方」「言わなくても分かること」は一切通じず、書かれていない箇所は AI が推測で埋めます。以下を揃えていただくと、ローカルLLMでも安定します。

| 項目 | 書き方 |
|---|---|
| 関数ごとの記述 | **呼び出し方（C のプロトタイプ）／目的／引数と制約／戻り値の値ごとの意味／成功時に保証されること／失敗時の状態** の6点を必ず書く |
| 数値 | 具体値で書く（「十分小さい」ではなく `1e-12`、「大きすぎない」ではなく `n <= 16`） |
| やらないこと | 明記する（動的メモリ確保をしない、標準入出力を使わない、スレッド非対応 など）。書かれていない禁止事項は守られません |
| 試験観点 | **ID 付きの一覧**（T01, T02, …）で書く。境界値（要素数 0・1・最大、最大値・最小値、特異行列 など）を含める。そのまま単体試験になります |
| 図 | 画像ではなく **Mermaid（文字で書く図）** にする。既存の画像は OCR → 本文と照合 → Mermaid に書き直します |
| 未確定事項 | **【要確認】** と書く。空欄にせず、AI に書かせる場合も同じ印を付けさせる |

章立てのテンプレートと記入例は、リポジトリの `docs/01` にまとめています。

## 5. 検証結果（数値）

すべて自作のダミー資料（C 言語の整列・連立一次方程式ライブラリ）で実施しました。**貴社の実資料は一切使用していません。**

| 工程 | 所要時間 | 備考 |
|---|---|---|
| PowerPoint（8枚）→ Markdown | 0.08 秒 | 見出し・箇条書き・表はそのまま。図は画像として別出力 |
| Excel（3シート）→ Markdown | 0.02 秒 | 各シートが表として出力。シート名のみ人が補記 |
| 図（画像）の文字読み取り（OCR 3 種を同じ図で比較） | 0.3〜4.9 秒 | Apple Vision 0.4 秒 ≧ Tesseract 0.3 秒（Linux）＞ EasyOCR 4.9 秒。日本語の文は読めるが、記号・添字は崩れる |
| 要件（10行）→ 仕様書（Nemotron） | 2 分 52 秒 | 10 章構成・試験観点 24 項目 |
| 要件定義書（PPT 8枚）→ 仕様書（Nemotron） | 2 分 40 秒 | 10 章構成・試験観点 20 項目・要件トレース表付き |
| 既存仕様書（PPT/Excel 変換）→ 仕様書（Nemotron） | 5 分 17 秒 | 原資料の試験観点を欠落なく引き継ぎ、補った箇所に【要確認】18 か所 |
| 仕様書 → 実装・単体試験・カバレッジ（Nemotron） | 26 分 40 秒 | **24 / 24 件合格、行カバレッジ 97.1%、関数カバレッジ 100%**（人手ゼロ。クリーンビルドで独立に再確認） |

参考として、最新の商用モデル（Claude）に同じ指示を与えて比較したところ、差は「試験観点の量」と「補足の丁寧さ」にあり、**正しさの差ではありませんでした。** 既存資料が具体的であれば、ローカルLLMで実用上十分と判断しています。

## 6. ご留意いただきたい点

1. **変換ツール（Docling）の既定の OCR エンジンは中国製（RapidOCR）です。** PowerPoint / Excel の文字と表を変換するだけであれば OCR は動作しませんが、画像やスキャン PDF を読み取る際は、OCR エンジンを明示的に指定してください（Linux / Windows では Tesseract を推奨。今回同じ図で実測し、日本語の文が読めることを確認しています）。手順書に明記しています。
2. **仕様書の穴は、そのままコードの穴になります。** 検証では、仕様書内の無意味な項目がそのまま実装され、未カバー行として残りました。AI に書かせた仕様書は「関数の呼び出し方」と「無意味な項目がないか」の2点だけ人が確認することをお勧めします。**要件定義に「データの渡し方・命名規則・エラーの返し方」を1枚添えておくと、この種の矛盾は発生しませんでした。**
3. **AI の完了報告は、実際より楽観的なことがあります。** 検証では「1回で完了」と報告しましたが、実際にはビルドと試験が通ったのは5回目でした。数値自体は正確でしたが、ビルド・試験・カバレッジの手順を AI が変更できないファイル（Makefile）に固定し、**人が同じコマンドで再実行して確認する**運用を前提にしてください。
4. **本資料の所要時間は、クラウド経由（OpenRouter）で同じモデルを動かした値です。** 手順・プロンプト・ルールはオンプレ環境でそのまま使えますが、処理速度は貴社の実機で別途計測が必要です。

5. **変換ツールは Microsoft 製の MarkItDown とも比較しました。** Excel はシート名が残る点で MarkItDown が優れ、PowerPoint は箇条書き・表・図の扱いで Docling が安定していました。主に Docling、Excel のみ MarkItDown、を推奨します。

## 7. 今後のご提案

- **貴社の実機で同じ手順を実行し、所要時間を実測する**（唯一、クラウドと異なる点です）
- 仕様書生成の後に「自己点検の1ターン」を加える（設計方針と関数定義の不一致、図の文法誤りをその場で直させます）
- 関数 10〜20 個規模の仕様書で試し、長時間タスクでの挙動と、作業を分割する運用の効き方を確認する
