# AI駆動開発と相性の良い仕様書の書き方

仕様書は AI への**唯一の入力**。書いていないことは AI が推測で埋める。「いつものやり方」「言わなくても分かる」は通じない。
詳しい解説と根拠は [詳細版](https://github.com/ARKLET-1111/ai-driven-spec-demo/blob/main/docs/)。

## 章立て（この順で、毎回同じ形で）

```
1. 概要            目的・対象言語・用途・前提（3〜5行）
2. データ構造・定数  型定義はコードブロック、定数は名前と値
3. API 一覧        表：# / 関数名 / 概要
4. 各関数仕様      ★本体（下の5点）
5. エラー処理方針   表：値 / シンボル / 意味
6. 非機能要件      スレッド・メモリ・計算量・精度
7. 使用例          10行程度
8. 単体試験観点    ★ID 付きチェックリスト（T01, T02, …）
9. ファイル構成    生成してほしいファイル名
10. 改訂履歴
```

見本：[リングバッファ仕様書](https://github.com/ARKLET-1111/ring_buffer_ai_unittest/blob/main/01_ring_buffer_spec.md)（この粒度で書けていれば十分）

## 関数ごとに必ず書く6点

| 項目 | 書き方 | 無いと AI は |
|---|---|---|
| シグネチャ | 実際の C プロトタイプ | 型や const を勝手に決める |
| 目的 | 1〜2行 | 何のための関数か推測する |
| 引数の表 | 引数／意味／制約（非NULL・範囲・破壊してよいか） | NULL チェックがばらつく |
| 戻り値 | 値ごとの意味（0 / -1 / -2 …） | エラーの種類を潰す |
| 事後条件 | 成功したとき何が保証されるか | テストの期待値が書けない |
| 失敗時の状態 | 入力・出力はどうなるか（変更されない／不定） | 半端に書き換えて返す |

## コツ（6つ）

1. **数値は具体値**：「十分小さい」→ `1e-12`、「大きすぎない」→ `n <= 16`
2. **やらないことを書く**：malloc 禁止、標準入出力なし、スレッド非対応。禁止されていないことは AI はやる
3. **境界値を書く**：n=0 / 1 / 最大、最大値・最小値、特異行列。そのまま試験観点になる
4. **図は Mermaid**：画像は AI に届かない。既存の画像は OCR → 本文と照合 → Mermaid に書き直す
5. **試験観点に ID**：AI がテストコードのコメントに書けるので、網羅を機械的に確認できる
6. **決めていないことは【要確認】**：空欄にすると AI が埋める

## どこまで細かく書くか

人が全部を関数レベルで書く必要はない。**AI に決めさせたくないことだけ人が書き、残りは AI に書かせて人が確認する。**

| 人が書く（契約と合否条件） | AI に任せる（中身） |
|---|---|
| 外から呼ばれる関数のシグネチャと約束事 | 内部の補助関数、アルゴリズムの細部 |
| 数値・禁止事項・エラーの返し方 | 変数名、ループの書き方 |
| 試験観点（合格の条件） | テストコードそのもの |
| データの渡し方・命名の方針 | 方針に沿った個々の判断 |

規模が大きければ2段：**人が要件＋方針を1〜2枚 → AI が関数レベルの仕様書 → 人は §4 のシグネチャと無意味な項目だけ見る。** 方針を1行ずつ書いた A2 では Nemotron の自己矛盾は出なかった。仕様を薄くした分はテストで受け止める（足して一定）。

## AI に書かせるときは

- **見本を1本渡す**（章立てと粒度は言葉より見本で伝わる）
- 決めたことには【設計判断】、推測には【要確認】を付けさせる
- 実装コードは書かせない（書き始めると仕様が薄くなる）
- **要件定義に「データの渡し方・命名・エラーの返し方」を1枚添える**。これだけで Nemotron の自己矛盾は出なかった（[実測](../pattern2_req_to_spec/COMPARISON.md)）
- 生成後に「§2 の設計判断と §4 のシグネチャが一致しているか点検せよ」と1ターン足す
